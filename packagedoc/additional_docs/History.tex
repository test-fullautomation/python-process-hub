\section{History}

\subsection{Version 1.1.0 - 06.02.2026}

Fleet Orchestrator -- multi-hub coordination overlay for managing multiple ProcessHub instances
across PCs from a central point.

\subsubsection{New Features}

\begin{itemize}
   \item \textbf{Fleet Orchestrator}: Central coordinator for hub discovery, health monitoring,
         and command routing across distributed ProcessHub instances
   \item \textbf{Hub Agent}: Lightweight sidecar alongside each ProcessHubServer that sends
         heartbeats, status reports, and handles fleet commands via the server's public API
   \item \textbf{Hub Registry}: Thread-safe registry with health state transitions
         (online $\rightarrow$ degraded $\rightarrow$ offline) based on heartbeat timeouts
   \item \textbf{Fleet Client}: High-level API for CI/CD pipelines and CLI tools, supporting
         single-hub commands and batch operations (start/stop/reset across all hubs)
   \item \textbf{Fleet Web API}: Optional REST API and HTML dashboard for fleet monitoring
         (FastAPI-based, served at configurable host/port)
   \item \textbf{Fleet Protocol Messages}: Typed dataclass messages extending MessageBase --
         HubAnnounce, HubRegistered, HubDeregistered, HubStatusReport, FleetCommand,
         FleetCommandResult, FleetStatusRequest, FleetStatusResponse
   \item \textbf{Fleet State Snapshots}: Frozen dataclasses (HubSnapshot, FleetStateSnapshot)
         with tuples for thread-safe concurrent access
   \item \textbf{Fleet Topics}: FleetTopics enum with FLEET\_ prefix for EventBus routing
         key separation from local hub topics
   \item \textbf{Event Callbacks}: FleetClient supports on\_hub\_online and on\_hub\_offline
         callbacks for reactive fleet monitoring
\end{itemize}

\subsubsection{Architecture}

\begin{itemize}
   \item Fleet is a pure \textbf{overlay} -- no modifications to core/, runtime/, or transport/ modules
   \item Each local ProcessHub works independently; the orchestrator is optional
   \item HubAgent uses only the server's public API (get\_state\_snapshot, handle\_start\_request,
         handle\_stop\_request, reset)
   \item Communication uses EventBus (RabbitMQ) with \texttt{fleet.*} routing key prefix in production,
         InMemoryTransport for testing
\end{itemize}

\subsubsection{Installation}

\begin{itemize}
   \item Added \texttt{fleet} optional dependency group: \texttt{pip install python-process-hub[fleet]}
   \item Fleet web API requires FastAPI and uvicorn
   \item Optional imports with \texttt{HAS\_FLEET} flag in ProcessHub.\_\_init\_\_
\end{itemize}

\subsubsection{Tests}

\begin{itemize}
   \item 76 new fleet tests across 5 test files (models, hub\_registry, hub\_agent,
         orchestrator, fleet\_client)
   \item All tests use InMemoryTransport -- no external dependencies required
   \item Total test count: 183 tests (107 existing + 76 fleet)
\end{itemize}

\subsection{Version 1.0.0 - 15.01.2026}

Initial release of ProcessHub as an independent package.

\begin{itemize}
   \item Migrated from ta-framework-tsb process\_hub module
   \item Clean architecture with separated core, transport, and runtime layers
   \item ZMQ transport with XPUB/XSUB broker
   \item In-memory transport for testing
   \item Console view for TUI display
   \item Process execution with platform-specific implementations
   \item Restart coordination state machine
   \item Logging server integration (Fluentbit, Telegraf)
   \item Comprehensive test suite (107 tests)
   \item Extended setup with CRepositoryConfig
\end{itemize}
